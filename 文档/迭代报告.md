## 2. 基线：原型落地（05-29）

**背景**：产品需求文档 v1.2 完成，需要一套可交互的高保真原型验证链路。

**交付**：三栏布局（状态导航 / 工单列表 / 工单详情）加底部聊天式输入框；SQLite 落库；CSV 与 Excel 导出；操作日志；5 条示例数据；4 份设计文档（产品设计、信息架构、用户流程、数据规则）。

**遗留**：识别默认走云端文本模型，等于"看得懂文字但看不见截图"；界面观感偏工程化；每次使用都要手动开服务。

## 3. 迭代 1：在线识别切换到智谱免费视觉模型（08-05）

**背景**：原默认模型只支持文本，用户粘贴截图后无法直接理解内容。

**改动**：

- 默认服务商改为智谱 `glm-4v-flash`（免费视觉模型），Base URL 指向智谱开放平台；
- 该系列不支持 JSON 模式参数，代码中对其跳过 `response_format`，改用严格提示词加宽松 JSON 提取；
- 保留 DeepSeek、通义千问、Kimi、GLM-OCR 等作为可切换项。

**结果**：截图可以直接被模型理解，无需先人工转述文字。

## 4. 迭代 2：识别方案收敛与失败保护（08-05）

**背景**：选项过多反而让人犹豫；另外识别一旦失败，输入框里的截图会被清空，需要重新粘贴。

**改动**：

- 识别方式收敛为两个顶层方案：本地 Ollama（免费离线）与联网识别（默认智谱，可换厂商）；
- 本地档隐藏 API Key 配置项，联网档才显示厂商与密钥；
- **识别失败时保留输入文字与截图**，并给出"跳过识别，直接创建草稿"的兜底入口；
- 模型缺失时提示具体修复命令（如 `ollama pull`）。

**结果**：识别失败不再丢失素材；配置界面从 8 项简化为按场景分组。

## 5. 迭代 3：一键启动（08-05）

**背景**：每次都要打开终端敲 `node server.js`，不符合"随手记录"的使用习惯。

**改动**：新增 `一键启动.command`（桌面 + 项目内各一份），具备依赖检查、端口占用检测、服务就绪等待、自动打开浏览器；未启动 Ollama 时给出提示但不阻塞。

**结果**：双击即用。

## 6. 迭代 4：性能优化（09-28）

**背景**：用户反馈"用起来很慢"。实测单条识别耗时 44 秒。

**诊断过程**：用同一张真实截图做对照实验，分别测试接口路径、图片尺寸、思考模式、模型冷启动四个变量。

| 对照项 | 耗时 |
| --- | --- |
| 原路径（兼容接口，默认参数，冷启动） | 44.1 s |
| 原生接口 + 参数调优（暖机） | 14.6 s |
| 2560px 大图 | 43.5 s |
| 1280px 压缩图 | 18.7 s |
| 纯文本（无图） | 5.3 s |

**结论**：主要成本是图片像素量（视觉编码）与模型冷启动，其次是接口参数未调优。

**改动**：

1. 发送前把截图等比压缩到最长边 1280px、转 JPEG（体积 652 KB 降至 80 KB）；
2. 本地识别改走 Ollama 原生 `/api/chat`：关闭思考模式、`num_ctx` 8192、`num_predict` 500、`keep_alive` 30 分钟；
3. 兼容读取 `content` 与 `thinking`，修复偶发空结果；
4. 新增 `/api/warmup`，切到本地档时自动预热模型；
5. 识别过程显示实时秒数。

**结果**：端到端从 44.1 秒降至 14.4 秒（约 3 倍）。

## 7. 迭代 5：macOS 系统 OCR（09-28）

**背景**：即使优化到 14.4 秒，逐条记录仍然偏慢；而截图里绝大多数信息是文字，让模型"看图"是不必要的开销。

**方案**：调用 macOS 原生 Vision 框架（与系统"实况文本"同源）先把截图转成文字，再让模型只做字段结构化。

**实现**：

- 编写 `tools/ocr.swift`（128 行），编译为原生二进制，首次使用时自动编译；
- 新增 `POST /api/ocr`（纯文字提取，不依赖模型）与 `POST /api/warmup`；
- 配置项"截图文字提取"三档：自动（本地识别时启用）/ 始终启用 / 关闭；
- 提取出的文字并入工单描述；跳过识别直接建草稿时也会自动补一次 OCR。

**结果**：端到端降至 7.6 秒；OCR 本身稳定在 200 ~ 300 毫秒。截图文字在无模型、无网络时同样可用。

## 8. 迭代 6：界面重构（09-28）

**背景**：用户反馈"页面设计不好看，交互效果不好"。诊断出的具体问题是：三栏挤压、卡片层级扁平、字段不区分已识别与待补充、失焦即存容易误改、操作缺少反馈。

**改动**：

1. **布局**：取消左侧状态栏，筛选改为横向胶囊条并入列表头部；列表为主视图，详情改为可收起的右侧抽屉；抽屉状态记忆。
2. **层级**：卡片重排为「状态色条 + 问题概括 + 弱化元信息」，优先级与来源用色点与轻标签表达；列表头部显示总数与今日新增。
3. **详情**：字段区分「已识别 / 待补充」，待补充用虚线高亮并统计数量；字段修改改为显式保存，可一键放弃。
4. **反馈**：识别进度条与秒表；新建工单高亮并滚动到位；抽屉滑入；按钮按压反馈。
5. **快捷键**：`Cmd+K` 聚焦输入、`J`/`K` 切换工单、`Esc` 收起详情、`Cmd+Enter` 提交。
6. **无障碍**：修正夜间模式按钮对比度（约 2:1 提升到 5.42:1）与字段标签对比度（4.27:1 提升到约 7.9:1）。

**结果**：列表在大屏可同屏呈现 3 列；详情区独立滚动不干扰页面；误存风险消除；双主题对比度全部达到 WCAG AA。

## 9. 迭代过程中的经验

1. **先量再改**：性能问题最初被归因为"Node 不好用"，实测后发现真正瓶颈是图片尺寸与冷启动，改动因此精准且低风险。
2. **善用系统能力**：macOS 自带的 OCR 比通用模型更适合这个场景，成本更低、速度更快，这是本次收益最大的一次改动。
3. **失败路径要和成功路径一起设计**：保留输入、兜底建单、明确报错，比事后补日志更有效。
4. **小而准的重构胜过大而全的重写**：本次没有引入任何前端框架，仅调整布局与状态机（显式保存），就显著改善了使用体验。
