# 工单记录小工具 · 技术大纲

版本：v2.3
更新日期：2026-09-28
适用范围：本地桌面工具（macOS），单机单用户

---

## 1. 项目定位

工单记录小工具是一款默认离线运行的本地记录工具，把 IM（企业微信、飞书、钉钉等）里的碎片化反馈，快速转成可追踪、可导出、可审计的结构化工单。

它不替代 Jira、TAPD、禅道等研发协同系统，而是作为反馈进入正式系统前后的轻量记录层：

- 本地工单号负责工具内唯一标识；
- 外部工单号负责关联正式系统；
- 云端能力默认关闭，只有用户主动开启并配置后才调用。

## 2. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 运行环境 | Node.js v22（本机实测 v22.22.3） | 跨平台、零安装负担，本机已有 |
| HTTP 服务 | Node 原生 `http` 模块，手写路由 | 无框架依赖，首屏启动快 |
| 数据存储 | SQLite（better-sqlite3 ^11.7.0） | 单文件数据库，WAL 模式，免服务端 |
| 前端 | 原生 HTML / CSS / JavaScript | 无构建步骤，改完刷新即生效 |
| 样式方案 | CSS 变量 + `data-theme` 主题切换 | 双主题、玻璃质感、无预处理器 |
| 本地视觉模型 | Ollama（默认 qwen3-vl:4b） | 完全离线、免 API Key |
| 云端识别 | OpenAI 兼容 Chat Completions | 一套协议适配智谱、DeepSeek、通义、Kimi |
| 系统 OCR | Swift + Vision 框架（macOS 原生） | 毫秒级、离线、中文识别质量高 |
| 启动方式 | 桌面 `.command` 脚本 | 双击即用，无需命令行 |

不引入构建工具与前端框架是刻意选择：这个工具的价值在于"随手可用"，任何需要 npm install、需要编译、需要联网拉包的环节都会降低使用意愿。

## 3. 系统架构

```
┌────────────────────────── 浏览器（单页应用） ──────────────────────────┐
│  index.html  结构骨架 + 主题预加载                                      │
│  styles.css  设计令牌、双主题、布局、动效                                │
│  app.js      状态管理、渲染、事件、识别调度、导出                        │
└───────────────┬────────────────────────────────────────────────────────┘
                │ fetch（同源，仅本机 127.0.0.1）
┌───────────────▼────────────── 本地 Node 服务（server.js） ─────────────┐
│  路由层    /api/* 与静态资源                                            │
│  业务层    工单 CRUD、附件落盘、导出数据组装                             │
│  识别层    Ollama 原生调用 / 云端兼容调用 / 系统 OCR 调度                │
│  存储层    better-sqlite3（tickets.db）+ attachments/ 目录              │
└──────┬────────────────────────┬───────────────────────┬────────────────┘
       │                        │                       │
   本地 Ollama             云端 LLM 接口            macOS Vision OCR
  127.0.0.1:11434        （智谱/DeepSeek 等）      tools/ocr 原生二进制
```

设计要点：

1. **浏览器不直连模型厂商**。所有识别请求经本地服务转发，密钥留在本机，同时规避浏览器跨域限制。
2. **识别是可插拔的一层**。本地模型、云端模型、系统 OCR 三种能力由配置决定，互不耦合，任一路径失败都不影响工单落库。
3. **存储是唯一事实来源**。前端每次操作后从 `/api/tickets` 重新拉取，避免本地状态与服务端漂移。

## 5. 数据模型

### tickets（工单主表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键，自增 |
| local_id | TEXT | `LOC-{UUID v4}`，唯一，不可编辑 |
| reporter / summary / description / context / menu_path | TEXT | 识别字段，可人工校正 |
| report_time | TEXT | 反馈时间，识别失败取当前时间 |
| status | TEXT | 待处理 / 已处理 / 待验证 / 待反馈 |
| external_id / handler / remark | TEXT | 人工维护字段 |
| priority | TEXT | 低 / 中 / 高 / 紧急 |
| ai_source | TEXT | local / cloud，标识识别来源 |
| created_at / updated_at | TEXT | 时间戳 |

### ticket_attachments（附件）

记录所属工单与文件名，实际图片按 `attachments/{local_id}/` 落盘。

### ticket_logs（操作日志）

以文本形式记录创建、字段变更、状态变更，追加式写入，用于审计与复盘。

当前数据规模：工单 7 条，附件 10 条，日志 21 条。

| 方法 | 路径 | 用途 |

| GET | `/api/status` | 服务健康检查 |
| POST | `/api/shutdown` | 关闭本地服务（脚本与设置页使用） |

| POST | `/api/ocr` | 只做系统 OCR 文字提取，不依赖任何模型 |
| GET | `/attachments/*` | 读取本地附件文件 |

## 7. 识别链路

### 7.1 统一流程

```
粘贴文字 / 截图
     │
     ▼
图片预处理：等比缩到最长边 1280px、转 JPEG（质量 0.82）
     │
     ▼
是否需要系统 OCR？
     ├── 需要（本地模式默认开启）→ macOS Vision 提取截图文字（200 ~ 300 ms）
     └── 不需要 → 保留图片，交给视觉模型
     │
     ▼
结构化：交给本地 Ollama 或云端模型，输出固定字段的 JSON
     │
     ▼
字段归一化 → 生成 LOC 工单号 → 写入 SQLite → 附件落盘 → 前端高亮展示
```

### 7.2 三条识别路径

| 路径 | 调用方式 | 适用场景 | 实测耗时 |
| --- | --- | --- | --- |
| 本地 Ollama + 系统 OCR | 原生 `/api/chat`，纯文本入参 | 默认推荐，离线、免费 | 约 7.6 秒 |
| 本地 Ollama + 视觉 | 原生 `/api/chat`，图片入参 | 需要模型直接读图时 | 约 14.4 秒 |
| 云端兼容接口 | OpenAI 兼容 `/chat/completions` | 追求质量或没有本地模型 | 取决于厂商 |

### 7.3 本地模型调用参数（性能关键）

```js
{
  model: "qwen3-vl:4b",
  think: false,                 // 关闭思考模式，避免无效推理
  format: "json",               // 强制 JSON 输出
  keep_alive: "30m",            // 模型常驻内存，避免重复加载
  options: { num_ctx: 8192, num_predict: 500, temperature: 0.1 }
}
```

同时兼容读取 `message.content` 与 `message.thinking` 两个字段：思考型模型有时会把结果写进 thinking，只读 content 会拿到空结果。

### 7.4 云端适配差异

| 厂商 | 处理方式 |
| --- | --- |
| 智谱 GLM-4V 系列 | 直接传图片；该系列不支持 JSON 模式参数，跳过 `response_format` 并做宽松解析 |
| 智谱 GLM-OCR | 先调 `layout_parsing` 把截图转文字，再用文本模型结构化 |
| DeepSeek V4 | 官方接口按文本处理，图片不直接发送 |
| 通义 / Kimi / 自定义 | 按 OpenAI 兼容多模态格式传图 |

## 8. 前端架构

- **状态**：模块级变量（工单数组、当前选中、草稿附件、待保存修改）加统一重渲染，规模小、逻辑直白。
- **主题**：`<html data-theme>` 配合 CSS 变量；页面加载前有一段内联脚本先定主题，避免刷新闪白。
- **布局**：列表为主视图 + 右侧详情抽屉；抽屉状态存 localStorage。
- **保存策略**：字段改动先进待保存集合，点"保存修改"才落库并写日志，避免失焦误存。
- **交互反馈**：识别进度条与秒表、新建工单高亮并滚动到位、按钮按压缩放、抽屉滑入。
- **无障碍**：全站 `:focus-visible` 焦点环、`prefers-reduced-motion` 与 `prefers-reduced-transparency` 降级、正文与按钮对比度均达 WCAG AA。

## 9. 安全与隐私

- 默认离线：不联网、不上传截图与文本，除用户主动开启的联网识别外无任何外发请求。
- 密钥不出本机：仅存于浏览器 localStorage 并随识别请求发往本地服务，由服务转发给厂商，不落库、不写日志。
- 数据脱敏：联网发送前对手机号、邮箱、身份证号、银行卡号做掩码（默认开启）。
- 路径安全：静态资源与附件读取均做路径归一化与目录前缀校验，阻止目录穿越。

## 10. 运行与部署

```bash
# 方式一：双击项目根目录的 start.command，自动起服务并打开浏览器
# 方式二：命令行
cd <项目根目录>/code
node server.js          # 默认 http://127.0.0.1:4173
```

服务只监听 `127.0.0.1`，不对外网开放。首次使用系统 OCR 会自动编译 `tools/ocr`（需要已安装 Command Line Tools）。

## 11. 已知限制

| 项 | 现状 | 影响 |
| --- | --- | --- |
| API Key 存储 | 浏览器 localStorage | 原型阶段的妥协，正式版应接系统密钥库 |
| 日志结构 | 文本记录 | 检索与统计能力有限 |
| 附件表 | 仅存文件名 | 未持久化 OCR 文本，无法回溯 |
| 状态流转 | 任意状态可切换，仅记日志 | 未做状态机约束 |
| 搜索筛选 | 前端内存过滤 | 数据量上千条后需改为服务端查询 |
| 系统 OCR | 仅 macOS | Windows / Linux 需替换 OCR 方案 |
| 协作 | 单机单用户 | 无多端同步与冲突处理 |

## 12. 后续演进建议

1. 密钥迁入系统密钥库（macOS Keychain），移除 localStorage 存储。
2. 操作日志结构化（字段名、旧值、新值、操作人），支撑审计与统计。
3. 附件表持久化 OCR 文本，支持全文检索与二次识别。
4. 引入状态机校验，减少状态跳跃造成的审计混乱。
5. 数据量增长后，将搜索与筛选下沉到 SQLite 查询。
6. 若需分发给他人使用，用 Tauri 打包为原生应用，免去命令行与终端窗口。
